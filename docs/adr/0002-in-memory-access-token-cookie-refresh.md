# Access token e refresh token só em memória, enviados explícitos no corpo da requisição

**Correção (ver `sentinel-auth-api` ADR-0014):** uma versão anterior deste ADR afirmava que o refresh token "não é um campo do corpo da resposta" e que o cookie era o único canal. Isso estava errado — o `sentinel-auth-api` entrega o refresh token em **dois** lugares desde o próprio ADR-0009 dele: no cookie `httpOnly`/`Secure`/`SameSite=Strict` **e** num campo `refreshToken` simples no corpo JSON de `login`/`refresh`. O próprio `docs/integrations/sentinel-auth-api-web.md` deste repo já documentava o campo do corpo corretamente o tempo todo; só este ADR que estava desatualizado.

Essa correção importa porque `SameSite=Strict` bloqueia o cookie em qualquer requisição cross-site — e este frontend (deployado na Vercel) e a API (deployada em outro host) são cross-site em produção. Um cookie `Strict` nunca é anexado nesse caso, independente de CORS ou de `credentials: 'include'`. Então o cookie não dá pra depender dele como transporte de refresh assim que frontend e backend ficam em sites diferentes.

Decisão: manter tanto o access token quanto o refresh token só em memória (React Context/refs), nunca em `localStorage`/`sessionStorage` — mesmo raciocínio de XSS de antes, um token em memória morre com a aba e é inalcançável a partir de um carregamento de página novo. No `login`, guardar o `refreshToken` vindo do corpo da resposta. Mandar esse valor de volta explícito no corpo das chamadas de `refresh`/`logout`, em vez de depender do cookie chegar sozinho. As requisições continuam usando `credentials: 'include'` de qualquer forma — inofensivo, e é o que faz o cookie funcionar de graça no caso same-site (dev local via proxy do Vite), sem nada pra mudar se frontend e backend algum dia ficarem same-site em produção.

Consequência: como nenhum dos dois tokens é persistido em lugar nenhum durável, e o cookie cross-site também não consegue restaurar uma sessão, um reload de página em produção desloga o usuário — não sobra nada de onde reconstruir uma sessão até ele logar de novo. Essa é uma troca aceita do modelo de ameaça só-em-memória, não um bug pra corrigir.
